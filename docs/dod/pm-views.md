## Purpose & typical use

1.1 — The users are the owner and anyone who installs dod from the public repository: a builder who plans features with dod in Claude Code, Codex or Cursor, several times a week, and the person they report to. What they would say: "show me how this plan did, in one page I can send to someone", "how is dod doing across all my projects?", "I want to send the maintainer a field audit without naming my client", "how long did that package take, and what did it cost in tokens?".
1.2 — The job: turn the plan files dod already keeps into the documents a project manager would hand round — analysis with charts, a KPI register, a work breakdown with versions and a schedule — in one recognisable look, for one plan, for one project, and across every project in a folder, without anyone copying numbers by hand.
1.3 — It replaces the plan page `dod-wbs.mjs --html <slug>` writes today (wbs-view, 2026-09) and restyles the review page (field-fixes D9, D17) without changing its content. It extends the field audit the maintainer receives as an issue (`.github/ISSUE_TEMPLATE/field-audit.yml`, release-0-3) with a page that fills it. It coexists with `--wbs` and `--export`, which are unchanged, and with every plan file, whose grammar is unchanged: effort lines are ordinary Log notes.

## Use cases

### Typical
A builder finishes work package W1.2 and the agent runs `dod-effort.mjs` for that window, which adds `- 2026-10-03 · note · effort · W1.2 · 22 min measured · 140 k tokens measured` to the Log (D21, D22). At close the agent regenerates `docs/dod/<slug>.html` and the dashboard (D26); the builder opens the plan page, sees the plan foresaw 87 % of the design with four numbered changes on the chart (D6, D7), and sends the page to their lead. Once a month they run the benchmark on their projects folder and see their median rate per project beside the overall median (D19), then paste the self-audit's issue block into a "Field audit" issue with no client name in it (D16–D18).

### Minimal stretch
8.1 — The least: a store with one draft plan, no reviews file, no effort line, no git. The plan page shows the faded baseline line labelled "draft", the rate as `n/a`, hours and tokens as `not recorded`, a schedule in days with the line "times from dates: git is not available" (D4, D7, D11); the dashboard lists one plan and prints `not recorded` for every mean and median, because no plan is done (D14, D15); the benchmark on a folder with no store exits 1 with one line (D20). A user who never runs the effort helper still gets every page, with effort `not recorded` (D4).
8.2 — Used once and never again: each page is one file the user can delete; store pages land in the store and are git-ignored in this lab (`docs/dod/*.html`), the benchmark is one file in the folder the user named; the effort helper keeps no cache and no state, and its selftest deletes its `<tmp>/dod-effort-*` folder on every exit (D24, D33). Nothing lingers or nags.

### Maximal stretch
9.1 — Volume: this store holds 45 plan files and 3.7 MB of plans, the largest 252 KB; the plan page of that one renders in under 2 s (13.1). The benchmark stops at 200 projects or 5,000 plans with a line (D20); at today's sizes 5,000 plans is about 400 MB of text, which the benchmark parses one file at a time, keeping only each plan's summary row — so memory follows the largest plan, not the store (D20's 100 MB fixture). The session records on this host are 3.9 GB in 854 files; the effort helper opens only files changed since `--since` and streams them, so a one-day window reads the day's files only (D24). A plan with 500 items still renders, with the Items table paged by the browser's own scrolling rather than by the page.
9.2 — Abuse: a folder swapped for a link between the walk and the read is caught by the `realpathSync` check before each open (D20); a plan title, a folder name or an amendment why holding markup cannot run in the page (D5) and cannot make it fetch anything, because the CSP meta forbids every request (D2); a sha field holding `--upload-pack=…` never reaches git (D11); a pointer `dod-store: ../../elsewhere` cannot pull another folder into the benchmark (D20); a link or junction in the walked folder is never followed, so a loop or a path outside the folder cannot be reached (D19); a session record holding a secret cannot leak through the effort line, which carries numbers only (D23).
9.3 — Repeated use: every page is a pure function of its files and git's answers — rendering twice gives the same bytes, apart from nothing (no clock is read; the dates come from the plan) (D6, D14); the effort helper run twice for the same package appends two lines, and the pages read the latest effort line per package, so a correction is a new line, never an edit (D22, Business rules 4.2); two benchmark runs write the same file through `writeUnderStore`'s rename, so a reader never sees half a page (D20).

## Business rules

4.1 — Calculations, each in one function of `dod-pages.mjs` and quoted on the page under its chart or in the KPI register's "what it means" column (D10, D15):
   - Prediction rate, completion and design changes are `reportNumbers`' values; `n/a` before `in-progress` (D4, D10).
   - Rework = the misses whose amendment carries `reworks:`, written `r of m` over the plan's discovered and corrected amendments (D10).
   - Review rounds to approval = the reviews dated on or before `baselined`; `not recorded` when there is no reviews file (D4, D10).
   - Draft to done = from the `→ draft` line to the `→ done` line, in days; in hours and minutes when both ends have a commit time (D10, D11).
   - Items verified per day = current items verified ÷ the days from the first to the last `pass` line, at least 1 (D10).
   - Most-missed probes = the probes named by the plan's discovered and corrected amendments, most first, ties by probe number (D10).
   - Hours = the sum of the latest effort line's active time per package; tokens likewise; with `<r> of <n> packages recorded` when some are missing, `not recorded` when none is (D10, D22).
   - Rate target 90 % and floor 75 % (`RATE_TARGET`, `RATE_FLOOR`, S-12) (D10).
   - Mean and median: D15's rules (D15).
   - Active time: D21's 10-minute gap (S-9) (D21).
4.2 — Invariants: a page never shows a number the plan files do not support — a missing measure is `not recorded`, never 0 (D4); the rate, completion and design changes on every page equal the `--check` numbers line for the same plan (D10, D14); an effort line is never edited, only superseded by a later line for the same package (D22); every page makes zero requests (D2); the self-audit's issue block holds no name (D18).
4.3 — Time: Log dates are calendar dates without zone. Commit times come from git as ISO 8601 with their offset and are shown in the offset of the base commit, printed in the chart caption (`times are UTC−04:00`). The schedule places each leaf's bar from the end of the leaf that finished before it (or the build start, for the first) to the latest commit time of its items' last `pass` lines; the build start is the base commit (`note · base <sha>`), else the `→ in-progress` date; the planning row runs from the commit that added the plan file, else the `→ draft` date, to the build start (S-16). When any time is missing the whole chart uses days — never a mix (D11). The effort line's date is `--until`'s date in its own offset (D22). Nothing is retroactive: a plan closed before this child shows `not recorded` for effort.
4.4 — Precedence: the plan file wins over every other source — a commit time that would place a pass before the plan's own `→ ready` date is still drawn, but the Log date is shown beside it; `reportNumbers` wins over any number a page computes on its own (D10 fails on a difference); when two effort lines name one package, the later Log line wins (D22); when both instruction files of a project name different stores, the project is skipped and listed, never guessed (D20); `design.md` is authoritative for every token, and D1 fails when the stylesheet differs. D2 wins over any host: a Claude artifact is the generated file unchanged, CSP included, and dod makes no copy without it — a host that cannot show the page with its CSP gets the file to download instead (D2, D26). Exceptions are the owner's alone, recorded as `note · exception · … · owner: <decision>`.
4.5 — "Every" sets, each with what computes it, what it could miss, and who checks:
   - "Every page dod writes" (D2, D5) is the exported registry `RENDERERS` in `dod-pages.mjs` — plan, review, dashboard, audit, benchmark, each with its fixture — which `dod-wbs.mjs` › `main` dispatches through and which the offline and escape tests enumerate; a renderer that is not in the registry cannot be reached from the command line, and one that is gets both tests without anyone remembering to add them (D2, D5).
   - "Every project in the folder" (D19) is computed by the walk; it misses, by the owner's rule, a project deeper than 3, inside a hidden folder, or reached through a link; a hidden folder, `node_modules` and a link are listed under Skipped by name, and for depth the walk lists each folder at depth 3 that has subfolders as `not searched below depth 3` — it names the boundary, never a project below it, which it cannot know without reading deeper.
   - "Every record of this repository" (D21) is the records whose `cwd` is the repository or below it. It misses a session started in a parent folder (this host: 286 of 5,754 lines in one session, the spike) — a reversible choice with `--cwd <parent>` as its fallback (S-15) — and work done in Codex or Cursor, which keep no such record: the line says so and the user may write an `estimated` line by hand (D22).
   - "Every colour token" (D1) is the frontmatter keys of design.md under `colors:`, read by the test; a token used in CSS but absent from design.md is a second direction the test also checks.

## Design

### Data
3.1 — Inputs: plan files and reviews files (any bytes; `loadPlans` decides, field-fixes D5); `profile.md` (the miss history's project probes); `design.md` (D1, the test only); git's commit times (D11); the walked folder tree (D19); session records (D21). Validation: `--since`/`--until` must be ISO 8601 with an offset and `--since` before `--until`, within 31 days; `--gap` an integer 1–120; `--package` a leaf of the plan or `plan`; `--roots` an existing directory; `--out` inside the container (D20, D22, D24). The shape of the text each new scan runs over (project probe 3.1): `EFFORT_RE` runs over whole Log note lines, anchored; the benchmark's store test runs over directory entries, which may be links, junctions or names with any characters; the session scan runs over JSON lines that may be truncated, carry no `cwd`, or repeat (D19, D21, D22, D24). Invalid input has its own message, echoed through `plainText` (D5).
3.2 — Outputs: five HTML pages (D6, D13, D14, D16, D19), one status line per run in `statusLine`'s existing shape (D14, D19), the effort line on standard output and, with `--plan`, in the plan's Log (D21, D22), and the issue block, which the user copies — nothing is sent to another system by this child (D18).
3.3 — Persistence, for every artifact this child produces:
   - `<store>/<slug>.html`, `<store>/<slug>.review.html`, `<store>/dod-dashboard.html`, `<store>/dod-audit.html`: written by `writeUnderStore` into the user's store, owned by the user, kept until they delete or regenerate them; in this lab ignored by git through `docs/dod/*.html` (D6, D14, D16).
   - `<dir>/dod-benchmark.html`: written into the folder the user named, owned by them, kept until deleted; it is the one file this child writes outside a store, and it lists the projects' names, so it stays on the user's machine — it is never part of a repository by this child's doing (D19, D20).
   - The effort line: one Log line in the plan, tracked with the plan (D22).
   - Temporary files: `writeUnderStore`'s `wbs-<n>-<hex>.tmp` beside the target, renamed or swept; the selftests' `<tmp>/dod-pages-*`, `<tmp>/dod-effort-*`, `<tmp>/dod-wbs-*`, each deleted on every exit (D24, D33); the rehearsal clones `<tmp>/pmv-rb` and `<tmp>/pmv-mut` (D34, D36); D27's rendered set, `<tmp>/pmv-pages-*`, deleted on every exit by `page-check.mjs`.
   - The design spec and product record: `skills/dod/references/design.md` and `PRODUCT.md`, tracked (D25).
   - Review prompts and outputs under `<tmp>/dod-review-*` outlive the session by design; at close `docs/dod/pm-views.cleanup.sh` deletes those of recorded reviews only (D37).
   - The effort helper keeps nothing: no cache, no index of sessions (D23).
   - The five private Claude artifacts D38 publishes: owned by the Claude account of the session that publishes them (named beside each link in the Log), visible to that account only, kept as the record of the owner's acceptance until the owner deletes them; they are copies of ignored generated pages, so a rollback neither needs nor removes them, and the cancel note lists their links for the owner to delete (D38).
3.4 — Migration: none. Existing plans render with the new page as they are; a plan without effort lines shows `not recorded`; no plan file is rewritten by any page mode (D4, D29).

### States
7.1 — Empty, first-run, partial, error: an empty store writes a dashboard and a self-audit that say `no plans yet` and exit 0, as `--export` does for an empty store (D14, D16); a draft plan (D4, D7); a plan with half its packages measured (`1 of 4 packages recorded`, D10); a benchmark with some projects skipped (D20); each fault of D11, D20 and D24 prints one line and never a pass.
7.2 — Concurrent use: two page renders write through `writeUnderStore`'s temporary file and rename, so a reader never sees half a page and the last writer wins (D20). The actors who can race here are the build tooling and the planner:
   - The agent appends an effort line while the user edits the plan, or two helper runs write at once: `writeAtomic`'s `expect` comparison refuses a write when the file changed since it was read, and the post-write re-read catches the change that lands between that comparison and the rename; the run that loses exits 1 and its line is written again by running it again — no lock, as dod's rule is, and never two silent successes with one line lost (D22).
   - A benchmark run while another session closes a plan in a walked project reads that plan before or after the close, never half, because plans are read whole; the page says when it was rendered by naming each plan's last Log date, not a clock (D19).
   - The effort helper reads a session file that the running session is still appending to; a truncated last line is skipped and counted (D24).
   - A sibling child (probe-fixes) may later edit `dod-wbs.mjs`; the rollback reverse-applies around it (D34).
7.3 — Stale data and re-entry: every page is regenerated from the files, so a page older than its plan is stale until the next render — the plan page states the plan's last Log date at its top (D6); an effort line written for the wrong window is corrected by a later line for the same package (D22); a correction to an amendment's kind recolours its circle on the next render; an interrupted helper run writes nothing, because the Log line is written by one atomic rename after the measurement (D22).

### Permissions
2.1 — Actors: the user and their agent, running the scripts on their own files with their own rights; a reader of a page (a lead, a reviewer, a stranger the user sends it to), who gets the HTML only; the maintainer, who receives only what the user pastes into an issue; CI, which runs the selftests read-only. The scripts add no privilege and no network. The effort helper reads only the user's own session folder; the benchmark reads only below the folder the user names (D19, D20, D21, D23).
2.2 — The unauthorised path: a page cannot run a plan's text or fetch anything (D2, D5); the benchmark refuses a store outside the named folder and lists it (D20); `--out` outside the container is refused with one line, as `writeUnderStore` does today (D20); the helper refuses `--config` outside a selftest (D21).
2.3 — Ownership: each page belongs to whoever generated it, from files they could read; a page sent onwards carries the plan's content, which is the sender's to share — the self-audit's issue block is the one output built for strangers, and it carries numbers only (D18). Effort lines belong to the plan; a later line from another person supersedes, never edits, an earlier one (D22).

### UX
11.1 — Where it lives: `page <slug>`, `page --dashboard`, `page --audit` and `page --benchmark <dir>` in SKILL.md's command table, each one `dod-wbs.mjs --html` mode; the effort helper is named in `start`'s builder rules (D26). Each run prints the path it wrote in its status line (D14, D19).
11.2 — Feedback: a status line per run (`html · <n> plan(s) · …`), one line per fault with its cause, `not recorded` and `n/a` instead of invented values, and the measured or estimated tag on every effort figure (D4, D20, D24).
11.3 — Accessibility and small screens: ARIA tabs with keyboard support and a no-script fallback (D3); every chart has an SVG `<title>`, a one-sentence heading and a "Show the numbers" table (D7); colour is never the only signal — every kind circle carries its number and the legend its word; contrast ≥ 4.5:1 in both themes, no sideways page scroll at 375 px, a visible focus ring (D27); charts scroll inside their own figure below 540 px (design.md).
11.4 — Activation: nobody has to ask for the pages — `close` regenerates the plan page and the dashboard and names both files, and the builder runs the effort helper after each work package because `start`'s rules say so (D26). The self-audit and benchmark are run when the user asks for a health check, an audit or a comparison; a request about something else, a code review or a test run, never triggers them.

## Security

10.1 — Authorization on every path: the scripts run with the user's rights and add no path that runs something on another's behalf. The one process spawned is git, with fixed arguments `["-C", <repo>, "show", "-s", "--format=%H %cI", ...shas]`, `shell: false` and a 10 s timeout, and every sha is matched to `^[0-9a-f]{7,40}$` first, so no plan text can become a git option such as `--upload-pack` (D11). The effort helper spawns nothing and imports no network module (D23). The benchmark follows no link and reads no store outside the named folder (D19, D20).
10.2 — Injection: every plan-derived string is escaped into HTML and cleaned for the terminal (D5); the CSP meta blocks script that escaping missed and every request (D2); folder names reach the page only through `esc` (D5).
10.3 — Secrets: none is read on purpose. The session records hold conversation text that may contain secrets: the helper reads only the counted fields and never prints, writes or keeps anything else (D23); the privacy scan runs over every changed file (D31); the effort selftest's fake key is assembled at run time so the source holds no token-shaped string (D31).
10.4 — Personal data: the benchmark page lists project names and stays on the user's machine (3.3). There is no access or share audit trail: dod cannot see who opens or forwards a file, so disclosure is the user's, and the page says so in its first line (D19); the issue block replaces every name with a number (D18); the effort line carries numbers only (D23); dry-run notes write `<home>` and `<tmp>` (D31).

## Failure & observability

12.1 — What the user sees: a page that says `not recorded`, `n/a` or `times from dates: <reason>` where data is missing (D4, D11); a Skipped tab for the benchmark (D20); one line and exit 1 for each refused input (D20, D22, D24).
12.2 — What is logged: each run's status line names the command, the plan count, the summary and the skipped count (D14, D19); the helper's line carries the session-file and skipped counts (D21, D24); the effort line in the Log is the durable record (D22).
12.3 — How the owner knows it is broken: CI runs both new selftests through `selftest-all.mjs` and `validate` on every push (D30); `junction-run` proves the installed path (D39); `release-check.mjs issue-form` runs in CI and fails on form drift (D17); the self-audit's Health tab shows check problems and a stale index (D16).
12.4 — Failing cases: every check this child introduces names in its item's `fails when:` the input that must fail it and the input it must stay silent on — D1 (a changed token), D2 (a planted image and import), D3, D4 (a `0 min` where nothing was recorded), D5 (markup in a title), D6–D12 (fixture plans with known answers), D13 (redaction words), D14, D15 (`[]` and an even count), D16, D17 (a renamed column), D18 (a client name), D19, D20 (seven planted faults), D21 (a tripled message, a sibling cwd, a 25-minute gap), D22 (a planted check problem), D23 (a fake key), D24 (eight faults and a 200 MB file), D27 (a planted request), D25, D29–D37, D39–D42. An empty input never reads as a pass: an empty store's dashboard says `no plans yet`, an empty root exits 1 (D20), an empty window exits 1 (D24). Before approval each item's command was run on the draft and its output recorded as a dry-run note. Each failing input today's code can take was run against it and its output recorded as a `note · spike · D<n>` line — the plan page without CSP or tabs (D2, D3, D6), a markup title through today's renderer (D5), a draft plan's page (D4), the issue form's header (D17), the duplicated session lines (D21, S-14). A check that does not exist yet runs its planted fault in the build step that writes it, its selftest keeps the plant, D36 turns each one off and D41 runs every gating plant in one command. Every tolerance cites its source: the 10-minute gap (S-9), the 2,048-byte script (the samples' script is 1.1 KB), the 200-project and 5,000-plan limits (S-20), the 64 MB heap bound (Performance 13.2), the 4.5:1 contrast (WCAG AA, page-check's `MIN_CONTRAST`).

## Performance

13.1 — Budget: a plan page under 2 s for the largest plan here (252 KB), the dashboard and self-audit under 5 s for this store (45 files), the benchmark of this workspace under 10 s, the effort helper under 10 s for a one-day window on this host (3.9 GB of records, of which one day is a few files). The hot paths are `parsePlan` per file and the session stream; git is called once per page with every sha in one command (D11, D19, D24).
13.2 — Limits: depth 3 (S-7), 200 projects and 5,000 plans (S-20) — at the bound the walk stops and says so (D20); a 31-day effort window, past which the helper refuses, because a longer window reads months of records for a figure no package needs (D24); one inline script of at most 2,048 bytes (D2); streaming reads keep the helper's heap growth under 64 MB whatever a file's size (D24). The valid cases these exclude: a project nested deeper than 3 (named by `--roots` on its parent instead), and a package that took more than a month (two windows, two lines — the later wins, so the user writes one line by hand with the summed figure marked `estimated`).
