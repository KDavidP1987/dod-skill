# DoD: index leak guard

**Size:** S, held deliberately — a tightly bounded cross-file maintenance change: one behaviour (the footer contract and its guard), touching the index module, the repo validator (one flag), one documentation section and the version manifests; no data-format change, one new user-visible line (the legacy-footer warning). The S test is satisfied on behaviour count, not file count.
**Planned:** interactively, from a dogfood finding on 2026-09-14: the generated `docs/dod/README.md` footer printed the store's absolute path — the developer's home directory — into a committed file in a public repo. Commit `6e3fd94` changed the footer to a cwd-relative path; nothing yet *guards* that contract, and a README committed by dod 0.1.0–0.1.2 still carries the old footer until someone regenerates it.
**Request:** "guard the generated index against leaking absolute paths: a test that fails if the footer ever goes absolute again, a warning when a committed README still has the old footer, and a leak scan of the generated files." Revision 2 after review 1 (9 findings; trust boundary, precedence and exception authority, footer escaping contract, evidence tightened). Revision 3 after review 2 (7 findings; cross-root stores, unreadable index, README size and encoding policy, 100× statement, cross-platform evidence, honest coverage pointers). Revision 4 after review 3 (5 findings; entropy failure, bounded read, escaping fixture inputs, sub-cases in the build step, rollback warning). Revision 5 after review 4 (5 findings; one rollback procedure, 400-file measurement placed in D3, symlinked README stated as a v0.1 limitation, selftest concurrency scoped to separate processes, drive-like components and Unicode format characters handled).

## Definition of Done
- [x] D1 · `renderIndex(plans, dir)` never emits an absolute path: for a store under the working directory the footer is `Store: \`<relative posix path>\``; for a store elsewhere on the same root it is a `..`-relative posix path; for a store equal to the working directory it is `.`; for a store on another root (a different Windows drive letter or a UNC share, where `path.relative` would return an absolute path) the footer carries no path at all and reads `Store: outside the working directory (see the dod-store: line in your instructions file)` — and in no case does the rendered text contain the home directory, nor does the footer path *begin* with a drive letter followed by `:\` or `:/`, a `/` or a UNC prefix (a later component that merely looks like a drive is allowed — see the drive-like rule below); the path is placed in the footer through one escaping rule — backticks become `'`, any C0/C1 control character, line separator or Unicode format character (category Cf, which includes the bidi controls) becomes a space — so a store path can neither close the code span, break the line nor reorder its display; a relative component that merely looks like a drive (`C:\leak` as a POSIX directory name) is not an absolute path and is rendered as-is, because the assertion is on the *whole* footer path being relative, and the test checks that after `Store: \`` the path does not begin with a drive letter, a slash or a UNC prefix · test: dod-index.mjs --selftest case index-relative (three store positions rendered; ## Purpose & typical use
- 1.1 The developer whose repo is public (every SkillEra repo) and the model regenerating the index after each plan write; the sentence: "the committed index must never tell the world where my checkout lives."
- 1.2 The job: make the relative-footer contract from `6e3fd94` permanent (a test), catch the READMEs already committed with the old footer (a warning), and prove no generated file carries the home directory or a secret (a scan).
- 1.3 Extends `dod-index.mjs` 0.1.2; coexists with the epic `dod-v0-2`, whose D16 leak scan covers the *v0.2* generated files (settings JSON, pointer block, wbs.md, wbs.csv, hook output) — this plan covers the one v0.1 generated file the epic's list omits, and the epic's `wbs-view` child should reuse the D3 scan helper rather than write a second one.

## Use cases
### Typical
The model writes a plan, runs `node <skill>/scripts/dod-index.mjs`, the README footer reads `Store: \`docs/dod\``; CI's `npm run validate` runs the selftest with the three new cases; a repo that still has a 0.1.2 README sees the D2 warning on its next `--check` and regenerates.
### Minimal stretch
- 8.1 Store equal to the working directory (`--dir .`): footer `Store: \`.\``. Store outside the working directory (a `dod-store:` pointing at a sibling folder): footer is `..`-relative; on another drive or share: the no-path sentence — in every case never absolute (D1).
- 8.2 One-time use: a store that never regenerates its README keeps the warning until it does; nothing else is written or nagged — the warning is the only state.
### Maximal stretch
- 9.1 Scale: the scan reads each generated file once per fixture — currently 4 READMEs of under 2 KB each (measured sizes, not bounds); the selftest asserts the count of scanned files equals the count of fixtures rendered, so a new fixture is scanned or the selftest fails. At 100× (400 fixtures) the scan is 400 files × 3 substring searches — linear in bytes scanned, results unchanged, well under 100 ms; the case `leak-scan` also runs the scan over a synthetic 400-file set to record that number (measured, printed, not asserted).
- 9.2 Concurrency: none new — the index write is the v0.1 `writeFileSync` (the epic's D35 `writeAtomic` will replace it; out of scope here).
- 9.3 Abuse: a plan title containing the developer's home path verbatim *would* trip the D3 scan for that fixture — by design the scan treats any occurrence as a leak; the selftest fixtures contain no such title, and a user's own plan text is theirs to write (the scan runs only on selftest fixtures, never on a user's store).

## Business rules
- 4.1 The footer is a cwd-relative posix path; `.` for the cwd itself; the fixed no-path sentence when cwd and store share no root (A-1, D1).
- 4.2 Invariants: no absolute path, home directory or seeded secret in any file the selftest generates (D1, D3); a legacy footer is a warning, not a problem, because it is a regeneration matter, not a plan defect (D2).
- 4.3 Precedence: a warning never changes lifecycle state or `--check` exit codes for plans; `--check-index` exits 1 for a legacy footer because the file is stale by content — the same rule as any stale index (D2).
- 4.4 ⛔ Precedence when rules conflict: (1) leak prevention — the footer is never absolute, whatever else is asked of it; (2) freshness — the README equals the current render, so a hand-edited or legacy footer is stale and is replaced on regeneration, never preserved; (3) message stability — warning text changes only with a version bump. Exceptions are authorised only by the plugin manifest's maintainer, through an amendment on this plan. Irreversible: none — every change is a test, a warning or a text edit; rollback is `git revert` (14.3).

## Interfaces
### Internal — reads / writes / changes (paths or symbols)
- 5.1 `skills/dod/scripts/dod-index.mjs`: `renderIndex` (footer already relative; D1 tests it), new `legacyFooter(dir)` helper used by `--check-index` and `--check`, new selftest cases `index-relative`, `index-legacy-footer`, `leak-scan`, summary line tokens (D4). `skills/dod/references/setup.md` `--check` section (D6). `SKILL.md` metadata.version; `.claude-plugin/plugin.json`; `.claude-plugin/marketplace.json` (D5).
- 5.2 Contract for consumers: `scanForLeaks(text, needles)` is exported so the epic's `wbs-view` and `autonomy-hooks` children can reuse it for D16; needles are plain strings, matched case-sensitively as substrings.
- 5.3 Nothing else reads the footer; the epic's D16 will extend the needle list (settings paths, `--shared` warning).

### External — dependencies and their failure behaviour
- 6.1 Node ≥ 20 (`os.homedir`, `path.relative`, `crypto.randomBytes`), already required. No git, no network, no npm package.
- 6.2 ⛔ Node absent → the v0.1 rule (`unverified by script`). The one new call that can fail is `crypto.randomBytes` (entropy unavailable or blocking): the selftest aborts with the fixed line `selftest: no entropy for DOD_TEST_SECRET` and exit 1, never printing a partial token, and its `finally` still restores `DOD_TEST_SECRET` and removes the temp store (D3). `os.homedir()` returning an empty string (rare CI sandboxes) → the scan skips that needle and prints `leak-scan: no home directory on this host` once; the other two needles still run (D3).
- 6.3 Test isolation: all three cases run inside the selftest's existing `mkdtempSync` store and remove it; `DOD_TEST_SECRET` is set on `process.env` for the selftest process only and deleted in `finally`.

## Design
### Data
- 3.1 Inputs: the store directory (already validated by `resolveStore`); the existing `README.md` — read through a bounded read of at most 1 MB + 1 byte from an open descriptor (so a file that grows between `stat` and read cannot be read past the cap); if the read fills the bound the file is over 1 MB and is not inspected ( `--check-index` prints `dod index: README.md over 1 MB — not a generated index; regenerate` and exits 1, `--check` warns the same and continues), decoded as UTF-8 with Node's replacement of invalid sequences by U+FFFD (such a file can never equal the render, so it is stale, and its footer is inspected as decoded — no crash, no second read), CRLF normalised, only the footer line inspected; `DOD_TEST_SECRET` (selftest only; if the environment already carries one it is overwritten for the process and restored after). A README with no footer line → not legacy, no warning; the freshness check handles it as stale.
- 3.2 Outputs: one warning line (D2); three summary tokens (D4); no new files.
- 3.3 ⛔ Persistence: nothing new is stored; the README is the user's generated file as before (regenerated on demand, deletable). The seeded secret lives in process memory for the selftest's lifetime and is never written anywhere — D3 proves exactly that.
- 3.4 Migration: a committed README with the 0.1.2 footer is migrated by regeneration; D2's warning is the prompt.
### States
- 7.1 No lifecycle change; the index has two states as before — fresh and stale — and a legacy footer is one *cause* of stale, named in the message. A missing README (first run) is stale with the existing `STALE or missing` message and exit 1 for `--check-index`, no warning for `--check`, and is never classified as legacy.
- 7.2 Concurrent regeneration: v0.1 behaviour (last write wins on a generated file; content is deterministic so both writers produce identical bytes). The selftest mutates the process-global `DOD_TEST_SECRET`; supported concurrency is separate processes (as `npm run validate` and CI run it) — two `--selftest` calls inside one Node process are not supported and the selftest says so in its header comment. A reader or `--check-index` racing the `writeFileSync` can observe a truncated README and report STALE for that instant — accepted as transient until the epic's D35 atomic writes replace the call; no retry is added here.
- 7.3 Re-entry: regenerating twice is a no-op; the warning disappears on the first regeneration.
### Permissions
- 2.1 ⛔ Actors and the boundary: the sole authorization boundary is the operating system's filesystem permissions on the repository — there is no user model, token or role inside the script. Who may invoke what: (a) the developer at a terminal — every form (regenerate, `--check`, `--check-index`, `--brief`, `--selftest`); (b) the model in the developer's session — the same forms, regenerate included, under the v0.1 show-then-run rule; (c) the CI runner — `npm run validate` only, which runs `--selftest` in a temp directory and never touches the repo's store; (d) the pre-push git hook, when a user has installed it — `--check-index` only, read-only. No job, webhook, export or other indirect path invokes this script; none is added.
- 2.2 Unauthorized path: a read-only README → the regenerate step fails with the v0.1 error (`EACCES` message, exit 1). An *unreadable* README (no read permission) → `--check-index` prints `dod index: cannot read README.md (EACCES)` on stderr and exits 1 (it cannot judge freshness); `--check <slug>` prints the same text as a `warn:` line and continues, since the plan check does not depend on the index; nothing is logged anywhere else (D2 case unreadable-index).
- 2.3 Ownership: the README belongs to the repo owner; the script never deletes it.
### UX
- 11.1 Reader: the developer at a terminal or reading CI output; the warning is one self-contained line naming the cause and the fix.
- 11.2 Failure text: `index footer carries an absolute path — regenerate with dod-index.mjs` — cause, then action, same shape as the existing STALE line.
- 11.3 Accessibility: plain text, no colour, ≤ 120 columns, meaning in words not layout (the v0.1 output rules).

## Security
- 10.1 ⛔ Untrusted input and paths: the README text is read, never executed or interpolated into a path; the footer is matched with an anchored regex; the store path comes from `resolveStore` as before and is the only path the script writes under. Symlinks: v0.1 follows them — a `README.md` that is a symlink is written through, a documented limitation of this version that the epic's D4/D35 (realpath-resolved store, atomic writes that refuse reparse points) removes; this plan does not widen it and states it in setup.md's `--check` section (D6). Every invocation path (2.1) sits inside the same filesystem boundary; no path bypasses it.
- 10.2 Injection: the warning prints no user text — only the fixed message; the one interpolated value in generated Markdown is the footer path, which passes through the D1 escaping rule (backtick → `'`, control characters and line separators → space) before it is placed inside the code span.
- 10.3 ⛔ Secrets: this plan's purpose. The scan (D3) proves the generated index contains neither the home directory nor a seeded secret; the secret is random per run and never persisted (3.3). The script reads no credential.
- 10.4 Data minimisation: the footer now carries only the store's position relative to the repo — information already in the pointer block (`dod-store: docs/dod`) — and nothing about the machine.

## Failure & observability
- 12.1 Failure classes: legacy footer → warning + `--check-index` exit 1 (D2); scan trips → selftest exit 1 with the needle's *name* (`home`, `tmpdir`, `secret`) and the file, never the needle's value (D3); no home directory on host → one info line, scan continues (6.2).
- 12.2 Observability: the three summary tokens (D4) make every CI run's result greppable; the warning appears in every `--check` until fixed.
- 12.3 Detection after release: `npm run validate` in CI on every push and pull request runs the selftest; the maintainer in `plugin.json` owns it (the same chain `plan-kinds` D20–D23 verifies).

## Performance
- 13.1 Budget: the selftest's added work is three renders and ≤ 18 substring searches over ≤ 6 small files — well under 50 ms; the existing selftest budget (no assertion in v0.1) is unaffected.
- 13.2 Limits: none new; the scanned set is bounded by the fixture count, asserted in D3's case (9.1).
