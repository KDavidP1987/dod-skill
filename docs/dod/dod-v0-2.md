## Purpose & typical use

1.1 — A developer or agent running a build of any size (one feature, a multi-component product, or a slice of an existing system) who says: "show me what done means here, keep the plan honest while I build, and tell me how far I am." Used at plan time, at every session start and end (hooks), and at close.
1.2 — Governance over N levels of work with one source of truth: a tree of plans whose leaves are evidenced items, rolled up into progress, provenance and prediction figures; the plan is kept current by the agent because the hooks make forgetting visible, not because the developer remembers.
1.3 — Extends dod v0.1 (`skills/dod`, commit bd220c3): two-level Epic → child, binary items, session-start brief only, model-performed setup. Coexists with the user's own backlog tools (Notion, Obsidian, issue trackers) by exporting, never syncing.

## Use cases

### Typical
A product with 3–5 levels (product → component → feature → sub-feature). Each node is a plan with `parent:`; leaves carry D-items. `--wbs` shows the tree with origin (baseline / discovered / requested / defect / external), one column per declared version plus baseline and now, and roll-up per node. At session end the Stop hook tells the agent — once — that Build-plan files changed after the last evidence, so it runs `status`/`amend` before finishing. `audit` runs before a milestone; `enhance` runs after a scope change.

### Minimal stretch
A single S/M plan with no `parent:` and no version lines: `--wbs` renders one node, two columns (baseline, now), identical in meaning to today's index row. A plan with zero D-items (a draft whose DoD is not yet written, or an Epic before its children exist) renders `—` for percent complete and for prediction rate with the reason `no items`, never a division by zero, and the roll-up treats it as contributing 0/0 (D37). A standalone defaults-only plan with exactly one D-item is the smallest meaningful calculation: unverified → 0 %, verified → 100 %, prediction 1/1 = 100 % with no amendments, asserted in the `zero-items` fixture alongside the zero case (D37). Hooks on a store with no in-progress plan exit silently. Used once and removed: `dod-setup.mjs --remove` deletes the hook entries, the pointer block, `.session/`, `wbs.md` and `wbs.csv`; the plans and the index stay (they are the user's documents); nothing nags afterwards because every autonomous path is silent without an in-progress plan. A v0.1 plan file is untouched and valid.

### Maximal stretch
Expected project: ~10 plans, 20–40 items each, 2–3 levels. 100× that — 1,000 plans, five levels, dozens of amendments, thirty versions — parses each file once, renders `--wbs` under 5 s (D14), shows eight most recent version columns with an elision note, warns above 24 columns under `--versions all` and still renders (D32); exports stream row by row with no cap (D23). `audit` on the whole store is linear in plans and resumable: each plan's audit line is appended as that plan finishes. Hostile input: a plan naming `rm -rf` as evidence is never executed by any script (the model shows it and asks); a `parent:` cycle, a `dod-store:` outside the repo, a CSV cell starting with `=`, a plan title containing `](` aimed at the WBS links, a 10,000-character line, reviewer output that asks the model to edit files — each refused, reported, escaped, or treated as data, with fixtures (D3, D4, D9, D23; reviewer output as data is the v0.1 rule).

### Backlog slice of an existing system
`kind: backlog` — the plan is "what remains before the testing team's first end-to-end wave", not the whole system. Recon reads the existing system and the user's backlog; items that already pass are verified at approve time (pass lines in Log order before `→ ready`) and marked pre-verified; the 15 layers are applied to the *readiness goal* (what must be true for the testers to start), not to each historical feature. The report separates pre-verified from built items so the prediction rate is not inflated by work that was already done.

## Business rules

4.1 — Origin is stored as `baseline` or an amendment id (`An`) on a Children row (absent = `baseline`) and, for a D-item, derived from the `+Dn` amendment that introduced it (none = `baseline`); it is displayed as the amendment's kind. "Discovered nodes" = children whose origin amendment has kind `discovered`. Node percent complete = verified items ÷ total current items in the subtree, integer percent (floor), unweighted. Node prediction rate = Σ baseline items ÷ (Σ baseline + Σ discovered design changes) over the subtree, per the v0.1 definition; a separately reported count "discovered nodes" = children whose Children origin is a `discovered` amendment. A version column shows each row's percent as of that version's date, counting only evidence lines dated on or before it. Column selection: baseline, the eight most recent versions by date (ties by Log order), now; `--versions all` lifts the cap.
4.2 — Invariants: the tree is acyclic; every `parent:` names an existing plan that lists the child; D-item IDs never reused (v0.1); version labels unique per plan and dates non-decreasing; `## Baseline` never edited; a pre-verified item still has a dated `pass` line with a `who`; an audit run id is unique per line; `kind` absent means `feature`.
4.3 — All dates are `YYYY-MM-DD` in the writer's local day; a version column's cut-off is end of that day; "changed after the evidence" for stale detection means a git commit dated after the evidence date, with a same-day commit treated as after (conservative). No time zones stored; day granularity is deliberate and documented in `references/wbs.md`.
4.4 — Precedence: the plan store's evidence lines decide done-ness. Exports and the WBS view are derived; external backlogs are never read, so the skill cannot and does not detect disagreement with them (the user reconciles by re-exporting). Drift means one thing: a parent's `## Report` figures differ from the roll-up — `audit` reports it, the roll-up wins and the report is regenerated. `audit` never writes outside the store. The script's `audit` never marks an item verified — only the model does, interactively, with a dated pass line. Exceptions are decided by the user through an amendment, never by a hook.

## Design

### Data
Plan files remain the only store (markdown, one per node). Additive grammar and CLI, all optional:

| Input | Shape | Validation | Invalid → problem text |
|---|---|---|---|
| `kind:` frontmatter | `feature` `product` `backlog`; absent = `feature` | enum | `kind "<v>" must be feature, product or backlog` |
| `parent:` frontmatter | slug of any existing plan, or `none` (v0.1: Epic only) | exists; lists this slug; acyclic | `parent <slug> not found` · `parent <slug> does not list <me>` · `parent cycle: a → b → a` |
| `## Children` row | `- slug · planned\|in-progress\|done[ · baseline\|An]` | slug regex; third field optional (absent = `baseline`); `An` must exist on this plan | `Children: line does not match the grammar` · `Children: origin A9 does not exist` |
| Log `version` line | `- YYYY-MM-DD · version · v<label> · <text>` | label unique per plan; dates non-decreasing | `version <label> is already used` · `version <label> dated before the previous version` |
| Log `audit` line | `- YYYY-MM-DD · audit · <run-id> · n/m verified · k stale · j unaccounted` | run id `[a-z0-9]{6}` unique per plan | `audit line does not match the grammar` |
| `## Proposed` section | bullets `- P-n · <layer or probe> · <proposed change> · <why>` | written only by `enhance`; never parsed into the DoD | `Proposed: line does not match the grammar` |
| `--wbs [--versions all] [--export csv\|md]` | flags | export destination is `<store>/wbs.<ext>` only | `export destination must be inside the store` |
| `--strip-v2 [--dry-run]` | flag | — | prints every removed or changed line |
| `audit [<slug>] [--auto]` | optional slug selects a plan and its subtree; none = whole store; `--auto` = the form the Stop hook runs: it may append audit lines inside the store and write `.audit-run`, and does nothing else — no evidence mutation, no write outside the store, no command execution; it prints nothing to stdout (its result is the audit line) and at most one stderr line | slug regex; must exist | `audit: no plan <slug>` |
| `enhance <slug>` | required slug | slug regex; must exist; plan must have a `requested` amendment or the user must have asked | `enhance: no plan <slug>` · `enhance: nothing changed scope — pass --force to run anyway` |
| `--wbs [<slug>]` | optional slug = subtree root | slug regex; must exist | `wbs: no plan <slug>` |
| `--brief` · `--check-index` | flags, no arguments | — | never non-zero (`--brief`); `--check-index` exits 1 on stale |
| `dod-store:` | path, may contain spaces | realpath inside the repository root | `dod-store resolves outside the repository` |
| hook stdin JSON | object with `session_id` (`[A-Za-z0-9_-]{1,128}`), ≤ 64 KB | parsed with a size cap; missing or invalid → SessionStart-only behaviour | one stderr line `hook: no session_id — brief only` |
| `dod-setup.mjs` flags | `--check` alone; `--auto-trigger` xor `--manual` xor `--remove`; `--hooks`, `--git-hook`, `--shared` may combine with the first two | mutually exclusive set enforced | `setup: --auto-trigger, --manual and --remove are mutually exclusive` |
| `--export --anonymise` | flag | replaces every `who` field with `agent` or `person` (agent ids are those the plan's Log names as the builder) | — |
| reviewer output (pasted by the model) | text; only lines matching `Fn …`, the coverage line and `VERDICT: READY\|REVISE` are parsed | no `VERDICT:` line → "no review"; anything else is data | `reviews: Review n has no VERDICT line` (v0.1) |
| plan file limits | ≤ 1 MB, ≤ 500 D-items, ≤ 10,000 characters per line | warnings, not problems; a line over the cap is reported and skipped by the renderer | `plan exceeds …` warning |

Outputs and side effects, exhaustively: generated `README.md` (index), `wbs.md`, `wbs.csv` under the store; appended Log lines (`audit`, `version`) in plan files — `enhance` appends no Log line: the `## Proposed` section is its only write and its own record (D22); `## Proposed` section in a plan; `.session/<session_id>` marker files under the store; `.claude/settings.local.json` (or `settings.json` with `--shared`) hook entries; the pointer block in the instructions file; the optional `.git/hooks/pre-push`. Deletions: `--remove` deletes exactly its own hook entries, the pointer block, `.session/`, `wbs.md`, `wbs.csv`, and the pre-push hook it installed — recognised by the marker line `# dod-index pre-push (installed by dod-setup.mjs)`; a pre-push hook without that marker, or with content beyond the installed block, is left untouched and reported (D10); marker files older than one day on every hook run. Nothing else is ever deleted; plans, reviews and the index are the user's documents and live in their git history.

Retention and deletion, per data class: plans, reviews, audit/version/enhance lines and `## Proposed` — owned by the user, retained as long as the repo keeps them, deleted with `git rm` (history remains unless the user rewrites it; the skill never rewrites history); generated files (`README.md` index, `wbs.md`, `wbs.csv`) — regenerated on demand, deletable at any time, `--remove` deletes the wbs files; `.session/` markers and the hook-health records D34 reads (one line per hook run in `<store>/.session/health.log`, user-owned, capped at the last 50 runs — older lines dropped on each write) — markers one day, health log 50 runs, both removed by `--remove`; atomic-write temp files (`.dod-tmp.<target name>.<pid>.<8 hex>` beside their target, D35 — the `.dod-tmp.` prefix is the signature) — normally renamed away within the same call; one left by a crash is user-owned, harmless (never read by any script) and deleted by the next run of any writer in that directory and by `setup --check`, which reports each deletion and deletes nothing that lacks the full signature (a user's `notes.tmp` is never touched); reviewer prompt files — written by the model under the OS temp directory as `dod-review-<store hash>-<plan id>-<date>.txt`, deleted by the model after the review is recorded, and — because a crash can skip that step — swept by every `dod-setup.mjs --check` and every hook run, which delete only prompts whose store hash is this store's and whose plan id is held by this store and that are older than one day; ownership is the pair (store hash, plan id), which is unique across repositories (D38); hook settings and pointer block — until `--remove`. Nothing is stored outside the repository except the temp prompt files.

### States
Plan lifecycle unchanged (v0.1). Derived states shown in the WBS: `pre-verified` (backlog items passing before `→ ready`), `stale` (evidence older than a Build-plan file change, per 4.3), `drifted` (a parent's Report differs from the roll-up, reported by audit). Hook states: silent, brief, nudge (once per session). Empty store, first run, malformed plan (row rendered with `?` and the parse problems listed below the table), interrupted audit (each plan's audit line is appended as it completes; the run id lives in `<store>/.audit-run` from before the first plan until after the last, so a rerun resumes that id and skips plans that already carry it — D21), crash before the next SessionStart (marker expires after one day; the next run cleans it — D29), cancel (a hook killed mid-run has written either nothing or one complete line, per D30). Re-entry after interruption is always safe because every write is either a single appended line (audit lines) or an atomic replace through the shared writeAtomic helper (D35) — the rewriting operations are exactly: enhance (Proposed section), strip-v2, exports, the index, setup's settings file and pointer block. Plan-file writers (audit line, enhance, strip-v2) follow one concurrency contract: read the plan, compute the new text, and immediately before the rename compare the file's current bytes with the bytes read; if they differ — an interactive edit, another script, an editor save — the writer discards its computed text, re-reads and recomputes, up to three times, then aborts with one stderr line `<command>: <slug> changed underneath — not written` and exit 1 (never overwriting the unexpected content); after the rename it re-reads and confirms its own change is present (D30). This covers a script racing a script and a script racing a person's uncommitted edit alike; a valid edit is never lost to a script. Readers that combine several plans (`--wbs`, `--export`, `--brief`, `audit` over a subtree, the index) follow the mirror contract: read every plan, compute, then re-read every source's bytes immediately before publishing; if any changed, recompute from the new bytes (three attempts) and otherwise abort with `<command>: store changed while reading — not written` (exit 1) for writers, or print with a trailing line `snapshot: inconsistent — <slug> changed while reading` for stdout-only forms, so a rendered result never silently mixes two versions of the store (D3, D23). The one path outside the contract is two people editing one plan by hand, where git is the merge tool (v0.1 rule).

### Permissions
Execution paths, each with its authorization boundary:
| Path | Runs as | May write | May execute |
|---|---|---|---|
| Interactive commands (plan, status, amend, close, audit, enhance, wbs) | the agent in the user's session | plan store; instructions file and settings only through `setup`, which prints before writing | evidence commands only under show-then-run, shown verbatim, confirmed by the user per command |
| SessionStart / Stop hooks | same OS user, non-interactive | `<store>/.session/`; plus deletion — never creation — of reviewer prompt files in the OS temp directory whose plan id belongs to this store (D38); nothing else | nothing — read-only queries via git; no evidence command ever |
| `audit --auto` (from the Stop hook) | same | one audit Log line per plan | nothing |
| CI (`npm run validate`) | GitHub Actions | temp dirs only (D26) | the selftests |
| Independent reviewer (Codex, subagent) | read-only sandbox | nothing | nothing — text in, text out; its output is data (v0.1 rule) |
| Readers of the public repo | — | — | — |
Unauthorized path: a hook or autonomous audit that would write outside the store, or would execute anything, is a code defect caught by D4/D5's spies; at runtime the store-resolution refusal is one stderr line and exit 0. The optional pre-push hook runs only `dod-index.mjs --check-index` (read) and fails the push on a stale index; it writes nothing.

Ownership (2.3), stated plainly: the skill has no user model and enforces no per-person rights — the repository's access control is the policy. Anyone who can write the repo can change or delete any plan, proposal, audit line or export; the Log line's `who` records who did, and git history is the audit trail and the undo. The skill's own deletions are exactly those enumerated in Design › Data. Concurrency: interactive commands are edits by one agent in one session; two sessions or two people editing the same plan are resolved by git (no locks — Out of scope 15.1); the one concurrent writer by design is the audit line, made safe by single-line appends and unique run ids (D30); `dod-setup.mjs` writes settings and the pointer block with temp-file-plus-rename, so two simultaneous setups leave a valid file with one entry (D15) and the later writer's other changes win — acceptable because the file is regenerated from flags, not hand-edited. There is no undo command; every write is a line in a git-tracked file.

### UX
Human-facing surfaces: `wbs.md` (tree table), `--brief` and the Stop nudge (one or two terminal lines, ≤ 120 columns), `audit` and `enhance` outputs (plain text), `wbs.csv`. All are non-interactive text; there is no keyboard or pointer interaction to make accessible. Discovery: SKILL.md command table, the pointer block, the index README's header. Feedback: every command ends with one status line (counts, file written, or "nothing to do"); long runs — audit, enhance, export over more than ten plans — print one progress line per plan to stderr (D33). Accessibility: markdown tables with header rows (read as tables by screen readers in editor previews), links as markdown links to plan files, meaning never carried by colour alone, no box-drawing characters in the brief; the checklist in `references/wbs.md` is the manual evidence (D24). Width: `--wbs` on a terminal prints the compact view — origin, baseline, now — fitting 100 columns (D32); the full matrix (eight most recent versions plus baseline and now, elision note, `--versions all` with a warning above 24 columns) is written to `wbs.md`, which is read in an editor or Obsidian where width scrolls. Reading order for assistive technology: header row first, one plan per row, depth as a leading indentation count in the first cell (`··· slug`), never as nested tables.

## Security

10.1 — Every execution path is inventoried in Design › Permissions with its boundary. Autonomous paths never execute anything and write only under the realpath-resolved store (D4); indirect paths — the pre-push git hook (reads the index only), `--export` (writes only `<store>/wbs.<ext>`), the reviewer (text only) — inherit the same rule. `setup`'s own destinations outside the store (`.claude/settings*.json`, the instructions file, `.git/hooks/pre-push`) are realpath-resolved with their parents and refused when they are links or resolve outside the repository root (D10). Store escapes through `..`, symlinks and directory junctions are tested (D4); setup's destination escapes are tested in its selftest (D10).
10.2 — No script builds a shell command from plan content: the scripts spawn only git with fixed argument arrays (D5); evidence commands are executed by the model, shown verbatim to the user first; paths from `dod-store:` and `parent:` are realpath-resolved and must stay inside the repository root; slugs are matched against the v0.1 slug regex before use in a filename; CSV/markdown cells are escaped (D23); every untrusted string bound for a terminal or a generated file has C0/C1 control characters stripped except the line separator, so hostile titles cannot forge output (D36). The remaining injection surface is the interactive show-then-run step, whose control is the user reading the command — the same as v0.1.
10.3 — The skill holds no credentials: no Notion token, no API key, nothing to rotate. The one credential in the vicinity is the user's Codex login, which Codex stores and uses when the model runs `codex exec`; the skill never reads, copies, passes or logs it, and no script invokes Codex (D5). Never logged (D27): environment variable values, more than the first line of any command output, absolute home paths. Hooks are written to `.claude/settings.local.json` by default so an absolute path containing the user's home directory is not committed; `--shared` opts into `settings.json` with a warning naming the path (D16). The design log stays under gitignored `.orchestration/`.
10.4 — Personal data, field by field: `who` on evidence and audit lines (a name or agent id the user typed) — minimised by convention to a first name or handle, exported as-is or replaced by `agent`/`person` with `--export --anonymise`; file paths — may include a home directory in `dod-store:` or the hook path, kept out of committed files by D16; free text in plans — the user's own content, not scanned or transformed. Retention follows the repo (Design › Data). No analytics, no telemetry, no network (D23).

## Failure & observability

12.1 — Failure classes (the full table with messages lives in `references/wbs.md`, D28):
| Class | User sees | Exit | Next action |
|---|---|---|---|
| store missing / unreadable | one stderr line naming the path | hook 0 · CLI 1 | run `setup` or fix `dod-store:` |
| malformed plan | `--wbs`: row with `?` and problems listed below; hook: one stderr line | hook 0 · CLI 1 | run `--check <slug>` |
| git absent / not a repo | stale and unaccounted checks reported as "skipped: no git" | 0 | none required; audit is partial and says so |
| git over 10 s | "skipped: git timed out" | 0 | rerun later; audit is partial and says so |
| hook over 2 s budget | one stderr line `hook: over budget, skipped` | 0 | run `--brief` by hand; check store size |
| store escapes repo | one stderr line | hook 0 · CLI 1 | fix `dod-store:` |
| reviewer unavailable | "review: pending — no reviewer available" | 0 | choose a reviewer or answer the rubric |
| Stop nudge (not a failure) | one stderr line naming the plan and changed files | 2 | run `status` / `amend`, then stop |
| hook contract missing (no stdin JSON) | brief only | 0 | none |
12.2 — Each audit run appends one dated `audit` log line with its run id and each version cut appends a `version` line, so that history is in git; `enhance` leaves its record in `## Proposed` — undated P-items by grammar; the section's history is the git history of the plan file, and `--check` reports the section's presence — and appends nothing to the Log (D22); `--brief` states index staleness; `--selftest` output enumerates fixtures and expected problems; every stderr line carries the plan slug and, for audit, the run id — enough to find the run in the Log without reproducing.
12.3 — Knowing it is broken: `npm run validate` (CI) runs every `--selftest`; a Stop hook that malfunctions shows as a nudge on every stop (marker not written) or never (hook not firing); `setup --check` is the operational health view — it reports the hook entry, the last marker time, per open plan the date and result of the newest audit line, and warns when the newest audit is older than 14 days or the last three hook runs ended in a failure class (D34).

## Performance

13.1 — Budget: `--brief` and the Stop hook under 300 ms on a 100-plan store and never over a 2 s total (they run on every session boundary); `--wbs` under 2 s at 100 plans and under 5 s at 1,000 (D14); hot path is parsing every plan file once — parse once per invocation, no recursion deeper than the tree depth (the cycle check bounds it); git is called once per audit, not once per item.
13.2 — Limits and bounds: version columns capped at eight most recent plus baseline and now with an elision note; `--versions all` lifts it and warns above 24 columns (D32); plan files are warned above 1 MB / 500 items / 10,000-character lines and over-long lines are skipped by the renderer (Design › Data); `audit` processes plans in slug order and appends each plan's line as it completes so an interrupted run loses nothing; `--export` streams one row per write with no row cap (memory is bounded by one plan at a time); markers older than one day are removed so `.session/` cannot grow.

## Rollout

14.1 — Ships in two releases (A4): skill 0.2.0 / plugin 0.4.0 after plan-readability, plan-accuracy, plan-kinds and wbs-view; skill 0.3.0 after autonomy-hooks, audit and enhance; no flag — the new commands are opt-in by invocation, hooks are opt-in by `setup --hooks`; the user turns hooks off with `dod-setup.mjs --remove`.
14.2 — Backward compatibility (old data, new script): `dod: 1` plans keep parsing — untitled items and `A-n` assumptions are warnings, never problems, so D2's v0.1 problem sets are unchanged — and `dod: 2` (titles, `S-n`) is reached only by `--migrate`; every v0.1 plan parses and renders as a single-node tree (D2); the v0.1 SessionStart hook JSON keeps working because `dod-index.mjs --brief` stays. Forward compatibility (new data, old script) is *not* claimed: v0.1's parser reports v0.2 Log bullets as grammar problems — which is why rollback has an explicit strip step.
14.3 — Rollback, in this order and while v0.2 is still installed: (1) `node <skill>/scripts/dod-setup.mjs --remove` — removes hook entries, pointer block, `.session/`, generated wbs files; (2) `node <skill>/scripts/dod-index.mjs --strip-v2` — removes exactly the v0.2-only lines from every plan and prints each one (D19); (3) clean reinstall at git tag `dod-v0.1.0` — the skill folder is deleted first because a checkout over it would leave `dod-setup.mjs`, `dod-hook.mjs`, `references/wbs.md` and `tests/fixtures/` behind: POSIX `git rm -r -q skills/dod && git checkout dod-v0.1.0 -- skills/dod`; PowerShell `git rm -r -q skills/dod; git checkout dod-v0.1.0 -- skills/dod` (`git rm` is the same on both and refuses paths outside the repo); for an installed copy, `npx skills remove dod` then `npx skills add KDavidP1987/skillera-skills@dod-v0.1.0 --skill dod`; (4) `dod-index.mjs --check` every plan. A store migrated to `dod: 2` is taken back first with `dod-index.mjs --migrate --to 1 <slug>` for every plan, which restores `A-n` and folds each item title back into its statement; dod: 1 → 2 → 1 is byte-identical (D40). Recovery: the stripped lines are in `<store>/.strip-v2/<slug>.removed.md` and in git history. Still possible after data has been written: yes — plans are text in git, and the strip step is tested against a store where every v0.2 data form has been written and then checked by the pinned v0.1 checker (D19).

## Out of scope

## Also considered

- Compliance / legal: the skill imposes no additional compliance regime of its own — it stores only what the user types into plan files, reviewer prompts and `who` fields, all inside the user's repository; any law that applies to that content (personal data in a `who` field, regulated text in a plan) is the repository owner's responsibility, exactly as for every other file in the repo. `--export --anonymise` exists so a shared export need not carry names.
- Localisation: dates ISO `YYYY-MM-DD` only; prose is English; integer percentages, no locale formatting.
- Running cost: each child plan costs one Codex review (~2–6 min, read-only); `enhance` costs one more per scope change; hooks cost one Node start per session boundary (< 300 ms budget).
- Operational ownership: the repo owner; nothing to page — failure is visible in CI (`--selftest`) and `setup --check`.
- Documentation / changelog: plugin version bump and README table (D25); `.orchestration/dod-design-log.md` carries the design history (gitignored).
- Analytics: none; the prediction rate and missed-layer aggregation in the index are the only measurements.
- Decommissioning: the model-performed setup procedure in `setup.md` is replaced by `dod-setup.mjs`; the old text is removed, not kept alongside.
- Support tooling: `setup --check`, `--wbs` and the audit line's run id are the support view — what the user saw is what is in the store.
