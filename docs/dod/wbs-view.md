# DoD: work breakdown — the tree view, the exports, the work-package section and the two HTML pages

**Size:** L — a new script (`skills/dod/scripts/dod-wbs.mjs`), a new plan-file section with checker rules in
`dod-index.mjs`, two export formats that write files, two HTML renderers, and a new reference document (L test:
it adds a grammar section every later plan must carry, it writes files outside the plan it reads, and its
rollback has to leave plans written under the new rule readable by the old checker).

**Planned:** the four decisions that shape it were answered by the owner on 2026-09-19 (AskUserQuestion, decision
page https://claude.ai/artifact/PuUDN2aEzmdiGyLo7zzMSk) and are recorded as validated assumptions; every other gap
is a labelled `reversible` assumption with its fallback.

## Definition of Done
- [x] D1 · **Tree view** `--wbs` prints the store as a tree of at least three levels — store, each epic, each child plan, and under a plan its work packages when it has them — where every node carries a name, an origin and the columns `baseline`, one per declared version, and `now`, each column holding `verified/total` and a percentage rolled up from the leaves; the tree is computed from plan files only, never from the index · test: dod-wbs.mjs --selftest fixture tree (a store of one epic, three children and one grandchild renders four levels with every parent's numbers equal to the sum of its leaves; a store with no epic renders two levels; a store whose `README.md` holds stale numbers that contradict every plan renders the plans' numbers and never the index's, and the same run with `README.md` deleted renders identically; fails when: a roll-up differs from the sum of its leaves, a level is dropped, or any index number reaches the tree)
- [x] D2 · **Version columns capped** A store declaring more than eight versions renders the eight most recent plus the line `… <k> earlier version(s) not shown — pass --versions all`; `--versions all` renders every one; more than 24 columns under `--versions all` prints `wbs: <n> version columns — this is wider than most terminals` once and still renders every column · test: dod-wbs.mjs --selftest fixture tree (ten versions → 8 columns and the elision line; --versions all → 10 and no warning; 30 versions with --versions all → the warning once and 30 columns; fails when: the cap is off by one, the elision line is missing, or the warning prints twice)
- [x] D3 · **Origin column** Every node's origin is the kind of the amendment that introduced it — `baseline` when it is in `## Baseline` or a `## Children` row marked `baseline`, else the kind of the amendment whose ops or Children origin names it: `discovered`, `corrected`, `requested`, `emergent`, `defect` or `external`; an item named by two amendments takes the earliest, and one named by none in a plan with amendments is `baseline` · test: dod-wbs.mjs --selftest fixture tree (all seven origin values render in one store; an item named by A2 and A5 shows A2's kind; fails when: a kind is rendered as another, an item added by an amendment still reads baseline, or the seventh value is missing)
- [x] D4 · **Snapshot is consistent or says so** `--wbs` reads every plan file, renders, then re-reads every file and compares the bytes it read; when anything changed it recomputes once from the second read, and when the second read also differs from a third it prints `wbs: the store changed while it was being read — this snapshot is inconsistent` above the tree and renders the last complete read · test: dod-wbs.mjs --selftest case wbs-vs-edit (a plan rewritten once between the two reads → the output shows the new content and no warning; a plan rewritten on every read → the warning line above a complete tree; fails when: a changed store renders the stale numbers or the warning appears for a store nobody touched)
- [x] D5 · **Compact terminal view** With stdout not a TTY, or with `--compact`, `--wbs` prints three columns — origin, baseline, now — and every line fits 100 columns for a slug of up to 40 characters, the name truncated with `…` when it would not; the full matrix goes to `wbs.md` · test: dod-wbs.mjs --selftest fixture tree (every compact line ≤ 100 columns for 40-character slugs at depth 4; a 60-character slug is truncated with … and still ≤ 100; the full view has more columns than the compact one; fails when: any line exceeds 100 columns or truncation drops the … marker)
- [x] D6 · **Roll-up never divides by zero** Percent complete is `verified/total` where total counts current items; a plan with zero items renders `—` with the reason `no items` in place of a percentage, and a parent whose every descendant has zero items renders the same rather than `0 %` or `NaN`; a prediction rate with no baseline and no discovered change renders `none`, and a one-item plan renders `0 %` before its pass line and `100 %` after · test: dod-wbs.mjs --selftest fixture zero-items (leaf with no items, epic whose three children all have none, one-item plan before and after its pass line; the same store's index and report lines asserted through dod-index.mjs; fails when: any output shows NaN, Infinity or a percentage over a zero denominator)
- [x] D7 · **CSV export escapes hostile cells** `--wbs --export csv` writes RFC 4180 rows whose every cell beginning with `=`, `+`, `-`, `@`, tab or carriage return is prefixed with a single quote, whose quotes are doubled, and in which a newline and a pipe survive inside the quotes — the one place D12's single-line rule gives way, because a quoted field is not a single-line record and RFC 4180 stops the newline starting a row, while every other control character is still removed; a 1,000-row export round-trips through a parser to the same values; an empty store writes the header row alone and says `export: 0 plan(s) · header only` · test: dod-wbs.mjs --selftest fixture export (cells `=cmd()`, `+1`, `-1`, `@here`, `a"b`, `a\nb`, `a|b` round-trip to themselves after the prefix is removed; 1,000 rows parse back to 1,000 rows; an empty store gives a one-line file and that status line; fails when: a formula-leading cell is written unprefixed, a quoted newline splits a row, or an empty store writes no file at all)
- [x] D8 · **Markdown export escapes links** `--wbs --export md` writes a header row, one row per node and a markdown link per plan whose text and target both escape `[`, `]`, `(` and `)` so a title containing `](` cannot make a link, and whose pipes inside cells are escaped as `\|`; an empty store writes the header and separator rows alone, with the same status line as D7 · test: dod-wbs.mjs --selftest fixture export (a plan titled `a](http://x) b` renders one link whose target is the plan file and whose text is inert; a title with a pipe keeps the table's column count; an empty store gives a two-line file; fails when: the rendered row has more cells than the header, a second link appears, or an empty store writes no file)
- [x] D9 · **Exports write under the store only** An export writes to `<store>/wbs.csv` or `<store>/wbs.md`, or to `--out <path>`, whose path is resolved before the write by walking it from the root down to the DEEPEST COMPONENT THAT EXISTS, calling `realpathSync` on that, and appending the not-yet-existing remainder to the result; the resolved path must lie under the store's own resolved path, so a link anywhere along the existing part is refused rather than followed, and a broken link on the path fails closed as a link. The final component is normally the one that does not exist yet — `wbs.csv` on a first run — so nothing can be resolved for it and nothing pretends to be (A15): its no-follow guarantee is carried at the open instead, by `O_CREAT | O_EXCL`, which fails `EEXIST` on a link that appeared in the meantime, and by the `fstat` / `lstat` comparison below. Three refusal classes, checked in this order and reported by the first that matches, so one destination can only ever print one line: (a) outside the store — `wbs: <path> is outside the store — exports are written under <store>`; (b) reached through a link — `wbs: <path> is a link — refusing to write through it`; (c) a destination that already exists and parses as a plan, or is the store's `README.md`, or matches `*.reviews.md` — `wbs: <path> is a plan file — exports are never written over plans`, which is what makes "it never writes a plan file" an invariant rather than a hope. Each exits 1 with nothing written; the write itself is `wbs-<pid>-<random>.tmp`, created in that same directory with `O_CREAT | O_EXCL | O_WRONLY`, plus `O_NOFOLLOW` on the platforms that define it — Windows does not, and `O_CREAT | O_EXCL` is what carries the no-follow guarantee for the final component everywhere, because an existing link there makes the open fail `EEXIST` — checked by comparing the handle's `fstat` inode against a fresh `lstat` of the resolved path, and their devices too whenever both stats report a non-zero one (Windows' `lstat` reports device 0 where `fstat` reports the volume serial, so requiring both everywhere would refuse every write there), and renamed into place — a run always removes its own temp file, and another run's only when `lstat`'s mtime is more than six hours before `Date.now()` — an mtime at or after now (a skewed clock, a synced or networked store) counts as fresh and is never swept — so a sweep cannot reach any writer that is inside its own performance budget · test: dod-wbs.mjs --selftest fixture export (each refused destination labelled with the one class it must print, so the ordering is asserted and not assumed: a destination above the store → (a) outside; `wbs.csv` replaced by a symlink to a file outside the store → (a), because outside is checked first; `--out linked/wbs.csv` where `linked` is a junction to a directory outside the store → (a); a link whose target is itself under the store → (b) link, which is the case that distinguishes (b) from (a); `--out docs/dod/wbs-view.md`, `--out <store>/README.md` and `--out <store>/wbs-view.reviews.md` each refused with the plan-file class and the target byte-identical afterwards, while `--out <store>/notes.md`, which is not a plan, is written; an existing link at the temp path making the open fail `EEXIST` rather than being written through; an identity check that passes on a host whose `lstat` reports device 0; a six-hour-old temp file present before a write and gone after; a one-minute-old temp file left untouched; a temp file whose mtime is in the future left untouched (clock skew never makes a file sweepable); a swap race — the target's parent replaced by a link to an outside directory while the write is in flight — in which the run either refuses with a named class or writes inside the store, with an assertion that the outside directory is empty in every ordering; a normal write leaving no temp behind; fails when: a refused path is created or written, a link on any component is followed, an export lands on a plan, a reviews file or the index, a fresh or future-dated temp file is swept, a stale one survives, or any ordering of the swap race puts a byte outside the store)

## Purpose & typical use
1. The owner of a dod store opens a tree once or twice a week to answer one question — where is this actually,
   and which part of it grew since the plan was approved. Today that answer lives in eight separate plan files and
   is assembled by reading them.
2. The job it does: turn a folder of plans into one picture of progress by package, and turn one plan into a page a
   human reviewer can read without also reading the author's own score.
3. What exists today: `--brief` prints one line per open plan and `README.md` is a flat table of plans. Neither
   shows a tree, neither rolls up, and neither renders a single plan for a reviewer. Both stay exactly as they are;
   this adds surfaces beside them and changes neither.

## Use cases
### Minimal stretch
1. A store with one plan and no epic renders a two-level tree with one row, and `--export csv` writes a
   two-line file. A plan with no items still renders, with `no items` in place of a percentage (D6).
2. Used once and never again: the two HTML files and the two export files sit in the store as ordinary files the
   user can delete; nothing schedules itself, nothing nags, and no state is kept anywhere else.

### Maximal stretch
1. Volume: 1,000 plans nested five deep with 30 items each — 100× this project's ten plans — parse once and render
   in under five seconds (D13). The hot path is reading and parsing files, not rendering.
2. Abuse: every string that reaches a line or a cell comes from a plan file the user controls, so the hostile input
   is a plan title carrying an ANSI escape, a newline, a CSV formula or a `<script>` tag; D12, D7, D8 and D19 each
   name the surface it cannot reach.
3. Repeated use: every command is a pure read and one atomic publication — two runs at once both complete, the last
   one wins, and rendering the same store twice produces byte-identical output (D10).

## Business rules
1. Percent complete of a node is `verified/total` over current items, rolled up as the sum of its leaves, never an
   average of percentages; the denominator is every current item, and `verified` is an item with a `pass` evidence
   line dated at or after its last `fail` — the same rule `--check` already applies, read from `dod-index.mjs` so
   the two can never disagree about a number the user sees twice.
2. Every "every X" set in this plan, how it is computed, what it misses and who checks it:
   *every node* = every `*.md` in the store directory that opens with a YAML front-matter block and parses as a
   plan, plus every work package in it. The front matter is the discriminator, so the store's own `README.md`,
   a generated `wbs.md` and any other prose file are skipped rather than reported, and the status line counts
   them (`skipped <n> non-plan file(s)`); a file that *has* front matter but does not parse is D27's failure,
   not a skip. Missed: a plan outside the store, or one whose name is not `<slug>.md`; D28's store diff is what
   would show a plan gone missing;
   *every probe* = `RUBRIC[rubric]` in `dod-index.mjs` (a probe added to `layers.md` without the constant is
   missed; the existing `rubric-sync` case checks the pair, and D21 renders probe text from `layers.md` so the
   page cannot drift);
   *every item* = `plan.items`, never `plan.baseline` (an item only in the Baseline is missed — deliberately, it
   is history; D15's ownership problems name every current item no package owns);
   *every string that reaches a surface* = the fields the renderer reads, each passed through `cleanLine` or the
   HTML escape at the one place the surface is built (a field a later change reads directly would be missed; the
   `control-chars` case of D12 plants a hostile title and asserts every one of the five surfaces, so a new
   surface added without escaping fails it);
   *every failure class* = the exported `MESSAGES` map (a class thrown as a bare error is missed; D24's
   `messages-match-table` compares the map to `references/wbs.md` in both directions and D27 asserts each one's
   line and exit status);
   *every write path* = the calls through `writeUnderStore` (a direct `writeFileSync` would be missed; D26's
   write-path scan is what fails on one);
   *every assertion a checker makes* = the exported `ASSERTIONS` registry each of the six checkers carries,
   which its own `--selftest` iterates (an assertion written into the code without an entry in the registry is
   missed; D33 fails a checker whose registry has an id with no planted violation, and the registry is the list
   the output counts, so a silent assertion shows up as a count that does not match the code review);
   *every section of a generated page* = the list D18 enumerates (a section the renderer forgets is missed;
   D18's fixture asserts each is present or absent-with-a-reason, and D21's asserts every probe id appears
   exactly once).
3. Authoritative documents: `layers.md` is authoritative for probe text and `RUBRIC` for probe counts (the
   `rubric-sync` case enforces the pair, which is why D21 reads probe text from `layers.md` rather than restating
   it); `plan-template.md` is authoritative for the work-breakdown grammar and `dod-index.mjs` for what `--check`
   makes of it (D14, D15, D16, D17); `references/wbs.md` is authoritative for the failure-class table, and D24's
   case compares it to the code rather than trusting either; and for the four path types `paths-walked.mjs`'s own
   definitions are authoritative while Rollout 4 is the citation — the checker parses the type words out of the
   inventory header it reads and exits 1 if they are not its own four, so this pair cannot drift either. Every
   duplicated definition in this plan has that shape: two places, one authority, one case that compares them.
4. Precedence, where two rules of this plan could both apply:
   *tree vs index* — the tree wins, because it re-reads the plans and the index is a generated snapshot (D1's
   stale-index fixture tests that the implementation obeys it, and D4 makes the tree say so when its own two
   reads disagree);
   *plan vs reviews file* — the plan wins for every number, because the numbers come from items, not reviews;
   *the single-line rule (D12) vs CSV quoting (D7)* — D12 wins on every **single-line record**: a terminal line,
   a markdown table cell, a status line, a progress line. A quoted CSV field is not a single-line record, so
   there and only there a newline is preserved inside the quotes, where RFC 4180 makes it unambiguous and it
   cannot start a row; every other control character is still removed, in CSV as everywhere else. Both halves are
   asserted in the export fixture;
   *refusing a link (D9) vs a link that stays inside the store* — refusal wins, and D9 is where it is tested:
   D9 turns away **any** link on the path, one whose target is under the store included, because the alternative
   is a resolve-then-write race and a second class of message for no gain.
   The owner decides any exception; there is no automatic resolution.
5. Temporal rules: version columns are ordered by the date on the `version` Log line, ties broken by the order they
   appear in the file; no time zone is involved there, because every date in a plan is a local date with no clock.
   The one place a clock *is* read is the stale-temp sweep, and it is read defensively: `lstat`'s mtime against
   `Date.now()`, sweeping only at more than six hours older, and treating an mtime at or after now — which a
   skewed, synced or networked filesystem can produce — as fresh, so skew can spare a stale file but can never
   delete a live one (D9).

## Interfaces
### Internal — reads / writes / changes (paths or symbols)
1. Reads, through `skills/dod/scripts/dod-index.mjs`: `loadPlans`, `parsePlan`, `reportNumbers`, `resolveStore`,
   `checkPlan`, `cleanLine`, `plainText`, `writeAtomic`, `RUBRIC`, `ID_LEGEND` — all exported today at b152504 —
   and `skills/dod/references/layers.md` for probe text. It also reads, never writes, the pinned checker
   `skills/dod/tests/fixtures/dod-index.v0.1.mjs`, which exists in the tree at b152504 and is what D30 and D32
   run the rolled-back store against.
2. Writes: `<store>/wbs.csv`, `<store>/wbs.md`, `<store>/<slug>.html`, `<store>/<slug>.review.html`, each through
   one guarded helper (D9), and nothing else. It never writes a plan file — not by omission but by refusal: D9
   turns away a destination that parses as a plan, the store's `README.md` or a `*.reviews.md`, so no plan can
   be damaged by a view even when the user points `--out` straight at one.
   `dod-index.mjs` gains the work-breakdown parser and its four checks; `plan-template.md`, `review.md`,
   `lifecycle.md` and `SKILL.md` gain text.
3. New contracts: the `## Work breakdown` section's grammar and the amendment's ` · package: W<n>.<m>` field
   (D14, D17), both inside the plan file, and the two generated HTML files, which nothing reads back.

### External — dependencies and their failure behaviour
1. Runtime: Node 20 or later and its standard library only — no npm package, no service, no vendor, no quota and
   no cost. The one external tool is Playwright's bundled Chromium, and its contract is: any `playwright` 1.x
   that ships Chromium 120 or later, resolved **once** at build time and written as an exact version into
   `scripts/checks/package.json` (`"playwright": "1.x.y"`, never a range), installed by the builder for that
   session with `PLAYWRIGHT_BROWSERS_PATH=`<the OS temp directory>/dod-wbs-browsers` npx playwright@<that version> install chromium`
   and never by a user of the skill. That path is the cache, stated once here and repeated verbatim in D32,
   Rollout 4 and the running-cost line: a fixed directory under the OS temp root, created if absent and reused
   if present, never derived from `HOME` and never inside the worktree. It is fixed rather than freshly made
   per run precisely so the download happens once per machine — a `mkdtempSync` directory would re-download
   Chromium on every invocation, or fail with `Executable doesn't exist`.
   `page-check.mjs` uses only API present since Playwright 1.30 — `chromium.launch`,
   `browser.newContext({ viewport, colorScheme })`, `page.evaluate`, `page.screenshot` — so the compatibility
   rule is checkable rather than a version guessed months ahead, and D20's evidence line records the resolved
   `playwright` version and the `browser.version()` it reported. It is dev-only, free and offline, and no shipped
   file imports it. Its accepted result contract is D20's assertions: a verdict per width-and-theme combination
   plus exactly four PNG files under `--out`; anything else — a partial result, a missing screenshot, an extra
   written file — is a failure.
2. Behaviour when a dependency is slow, down or returns garbage, including internal collaborators:
   *Chromium* unavailable, hung or returning a malformed verdict → `page-check.mjs` gives every browser call a
   finite deadline: 30 s to launch, 30 s to open a page, 60 s for one width-and-theme combination, and 180 s for
   the whole run. On a deadline it kills the browser process, removes any partial screenshot, prints
   `page-check: chromium timed out after <n> s (<stage>)` and exits 1 — a hang therefore ends within a known
   bound rather than never. D20 is then recorded as a `fail` with that class and the item stays unchecked;
   nothing else in the child depends on it and no shipped surface changes.
   *The filesystem* — a read that throws is D27's `cannot read <file> (<code>)`; a write, rename or `realpath`
   that throws is `wbs: cannot write <path> (<code>)`, exit 1, the target untouched; a directory that disappears
   mid-scan is the inconsistent-snapshot path (D4), not a crash. There is no retry and no timeout: every call is
   a local synchronous one, and a hung filesystem hangs the process, which the user interrupts — an interrupted
   run leaves at most one temp file, which the next write removes (D9).
   *`dod-index.mjs`'s exported helpers* — the collaborator that could return garbage. A `parsePlan` that returns
   no items, a `RUBRIC` missing the plan's rubric, or a `reportNumbers` result with a zero denominator are each
   handled as data, not trusted: D6 covers the empty and zero cases, D27's `does not parse` class covers a plan
   the parser rejects (D27), and a rubric the constant does not know is `wbs: <slug> declares rubric <n>, which
   this script does not know` with exit 1. The two scripts ship together in one skill folder, so a version skew
   between them is not possible.
   *A sibling agent or another process* editing the store while it runs is D4, and two exports racing is D10.
3. Test mode: every fixture runs in a `mkdtempSync` store; no fixture touches `docs/dod`, and D29's tree hash is
   what proves it.

## Design
### Data
1. Inputs, each with its shape, its bound and its response to an invalid value (D31): the store directory
   (`--dir` or the `dod-store:` line — an existing readable directory, else `no plan store at <dir>`); a slug for
   `--html` (1–64 characters of `[a-z0-9-]`, else a usage error before any read); `--out <path>` (at most 4,096
   characters, resolved under the store, else D9's refusal); and the flags `--wbs`, `--compact`, `--versions all`,
   `--export csv|md`, `--review`, `--selftest`. The plan files themselves carry `dod-index.mjs`'s `LIMITS` — 1 MB,
   500 items, a 10,000-character line — and a file past any of them **warns and still parses**; D31 is
   authoritative on that (D31) and this paragraph follows it, after A9 found the opposite written here
   and enforced by nothing until D31 was amended to say what the code does. Where each bound comes from and what it costs (13.2):
   the slug's 1–64 `[a-z0-9-]` is not a policy at all but the plan-file naming rule restated — a plan is
   `<slug>.md` in the store and `dod-index.mjs` already refuses to name one any other way (D31 holds that refusal), so the
   bound excludes only slugs the store could never hold, and widening it here without widening `dod-index.mjs` would break the
   pair;
   `--out`'s 4,096 characters is Linux's `PATH_MAX`, borrowed because no shorter number could be defended and a
   destination path is passed to the OS unchanged; it excludes a valid deeper destination on a filesystem whose
   own limit is higher; on Windows D31's 4,096 excludes nothing, because the OS refuses first at 260
   unless long paths are enabled — and the destination check is D9's — the bound is a floor that gives a named line instead of an `ENAMETOOLONG`, not the real limit;
   the three plan-file limits are **inherited, not chosen here**: they are `dod-index.mjs`'s and this child only
   reports them, which is why all three warn rather than refuse. Their excluded valid case is a real one — an epic
   store past 1 MB, a plan past 500 items, a long embedded table row — and what it costs is one warning line,
   nothing more. Whether they should refuse is a behaviour change for every existing store at once, so it is the
   epic's `plan-limits` child (its A15) rather than a decision taken here.
   Store depth, plan count and export row count are deliberately unbounded; D13 is the evidence. Exactly
   one mode per call; an unknown flag, a missing slug, two modes or an option that does not belong to the chosen
   mode prints the usage line and exits 1 before anything is read. A plan that does not parse is a named failure
   (D27), never a crash.
2. Outputs: stdout (the tree, the status line), stderr (progress lines), up to four files under the store,
   and — from `page-check.mjs` only, which is lab tooling and not a surface this child ships — four PNG
   screenshots in a directory under the OS temp root, outside the repository (D20, and item 3 for their
   lifecycle). Nothing else receives anything; no other system is involved.
3. Persistence: the four generated files are the only artifacts IN THE STORE (D20's screenshots are the
   other artifacts and are covered below), they live in the store beside the plans, they are
   owned by whoever owns the repository, they are kept until someone deletes or regenerates them — no expiry, no
   retention window — and they are overwritten by the next run. By-products: the temp file each write uses is
   renamed into place or removed on the same run, and one lifecycle governs a temp file left by an interrupted
   run, stated here and nowhere else: it belongs to the run that made it, that run always removes it, and another
   run removes it only once it is more than six hours old (D9) — so an interruption leaves exactly one file, and
   it survives until the first write that happens at least six hours later. The selftest's temp stores are
   removed at the end of the run; nothing is logged, so there is no log to keep. The plan files
   themselves are read-only to this child, which D9 makes true for `--out` as well as for the defaults. Only the
   two HTML files exist once per plan; the two export files
   exist once per store. The four screenshots of D20 are **build evidence that outlives its run**, and this
   paragraph said the opposite for a round after A19 decided otherwise (A22): they are written under `--out`
   when the builder passes one and otherwise into a `<the OS temp directory>/wbs-pages-*` directory the checker
   creates and PRINTS (A14, which made `--out` optional), they are owned by the builder, they are never
   committed and never written by shipped code, and they are KEPT — the run that produced them does not delete
   its own evidence, the inventory marks that directory `· outlives`, and whoever ran it removes it when they
   are done reading it. Nothing removes it on a schedule and nothing depends on it being gone. The durable
   record is still D20's evidence line in this plan, which names the assertions and the run's result; the PNGs
   are what a human looks at when they doubt the line. D20's command has two write scopes and asserts each separately: *page generation* writes exactly
   `docs/dod/wbs-view.html` and `docs/dod/wbs-view.review.html` into the store, declared in Rollout 4 like any
   other generated file, and *the browser run* writes exactly the four PNGs under `--out` and nothing anywhere
   else — so the lifecycle is checked rather than promised.
4. Migration: none. Plans without a `## Work breakdown` section keep working (D16), and no existing file's shape
   changes.

### Permissions
1. Actors: (a) the user — runs every command and owns every file it writes; (b) the agent — runs the same commands
   on the user's behalf and may write only under the store; (c) the script — reads the store and `layers.md` and
   writes the four files; (d) anyone who can read the repository — can read the generated files, which contain only
   what the plans already contain; (e) a reviewer given the review page — sees the plan without its scores (D22).
   There is no service account, no unauthenticated path and no network actor, because nothing listens and nothing
   is sent.
2. The unauthorized path is a filesystem path: a destination outside the store, or one reached through a link, is
   refused with its own line and exit 1 and nothing is written (D9) — the only way this child could write where it
   should not.
3. Ownership: the generated files belong to the repository like any other file; regenerating replaces them, and a
   file a second person made is simply overwritten by the next run — there is nothing to hand over, and no state
   survives a run. A plan's own ownership is untouched: this child never writes a plan.

### States
1. Empty and first run: no store → one line and exit 1 (D27); an empty store → `wbs: nothing to do`; a plan with no
   items → `no items` (D6). There is no loading state — one synchronous pass — and the partial state is the
   inconsistent snapshot, which is labelled (D4).
2. Concurrent use: two `--wbs` runs cannot conflict (both only read); two exports race and both publish completely
   (D10); a plan edited while the tree is read is the inconsistent snapshot (D4). The actor racing you here is
   usually *you* — the agent regenerating a page while the build is still writing the plan it renders — which is
   exactly why D4 re-reads rather than trusting its first pass. The guarantee about the stale-temp sweep is
   bounded, not absolute: it cannot reach a writer inside the performance budget (5 s for 1,000 plans, D13), but
   an export somehow still live after six hours can have its temp swept. That is outside the design rather than
   handled inside it, and the recovery is stated: the rename then fails with `ENOENT`, the run prints
   `wbs: cannot write <path> (ENOENT)` and exits 1 having published nothing, and the next run rewrites the file
   from the plans — no partial file is ever visible, because publication is the rename.
3. Stale data, cancel, re-entry: every command recomputes from the files on every run, so there is no stale cache to
   invalidate; interrupting before the rename leaves the target untouched and a temp file that the next run sweeps;
   a correction to a plan invalidates only the generated files, which are regenerated by running the command again.

### UX
1. Discovery: `--wbs` is named in `SKILL.md`'s command table and in `references/wbs.md`; the review page is named
   wherever a review is asked for (D23), which is where a reader actually needs it.
2. Feedback: progress lines while a large store is read, one status line at the end of every run, and one line per
   failure class with what to do next (D27); an empty store says `nothing to do` rather than printing an empty tree.
3. Accessibility: the terminal surfaces are plain text with no colour, fitting 100 columns (D5) and 120 for the
   one-liners; `wbs.md` uses header rows and links. The HTML pages are static documents — the only interactive
   element is a same-page anchor from the package tree to its item rows, so keyboard support is the browser's
   own tab order plus a visible focus ring, and there is no widget, no trap and no shortcut to define. For a
   screen reader they rely on structure, not ARIA: one `<h1>`, heading levels that descend without a skip, a
   `<table>` per section with `<th>` header cells and a `<caption>` naming it, and a text alternative nowhere
   needed because the page holds no image. Body text meets WCAG AA — at least 4.5:1 against its background in
   both themes — and every one of these is asserted by D20's command at both widths, not left to inspection.
   Meaning is never carried by colour alone: every state is also a word (D25).
4. Activation: the tree and the exports have no trigger at all, by decision — no hook, no schedule, nothing on
   `close` — and what shows one ran is the file it wrote and the status line it printed. The review page does
   have an activation, and D23 is what installs it: the pointer lines in `review.md` and `SKILL.md` make the
   agent generate the page *before* asking a human, and the path carried beside the question batch is what shows
   that it ran. That is the whole of it: a sentence in two documents, no code that fires on its own.

## Security
1. Authorization: there is no authorization to check, because there is no actor the filesystem does not already
   authorize — the script reads what the user can read and writes only under the store (D9). The indirect paths
   that would normally need a check (a job, a hook, an export) do not exist here: nothing invokes this child
   except a command, and `--export` is itself that command. D9 holds the path at the write, not only at the
   check: the temp file is created with `O_CREAT | O_EXCL | O_WRONLY` (and `O_NOFOLLOW` where it exists), so it can never be a
   link; the open handle's `fstat` inode — and its device where the platform reports one — must equal a fresh `lstat`, so a file
   swapped between the check and the open is caught; and the rename stays inside that same verified directory.
   The window this leaves is the parent **directory** being replaced by a link between `realpath` and the open,
   which portable Node cannot close (there is no `openat`). It is accepted, and this is why: to win that race an
   actor must already be able to create a directory inside the store's parent, and anyone who can do that can
   already rewrite every plan file in the store — the race grants no access it does not already have. D9's
   swap-race case proves the file-level half: with a directory replaced under a running write, D9 either stops
   with a named class or writes inside the store, and in no ordering does a byte land outside it.
2. Injection: every input reaches a terminal line, a table cell, a CSV field, a markdown link or an HTML document,
   and each has its own escape — control characters removed (D12), formula prefixes quoted (D7), link characters
   escaped (D8), HTML entities escaped (D19). No input reaches a query, a shell or a URL, because there is no
   query, no shell (D26) and no URL.
3. Secrets: none are read, stored, logged or printed, and D26 closes the sources and the sinks by name rather
   than by prose. The sources a credential could come from are the environment (only `DOD_SELFTEST_TIMING` is
   read, and the scan fails on a second `process.env` access), a home-directory or keychain file (no path under
   `~`, `%APPDATA%` or `.ssh` is read — the only readable roots are the store and `skills/dod/references/`) and a
   command's output (no process is started). The sinks one could reach are a network call (no network import, no
   fetch), a process argument (no process) and a generated file (whose every string comes from a plan file the
   user already owns). There is nothing to rotate or revoke, because nothing is held. A plan that itself contains
   a secret would render it — that is the plan's problem and `--check`'s leak scan, not this child's; the
   generated files never leave the machine.
4. Personal data: none is collected. The generated files contain only what the plan files already contain, and they
   stay in the repository the plans are already in; the audit trail is git.

## Failure & observability
1. Failure classes, each one line with what to do next: no store, unknown slug, unparseable plan, unreadable file,
   refused destination, inconsistent snapshot, usage error (D27) — and every one of them appears in the
   failure-class table of `references/wbs.md`, which D24 compares to the code in both directions.
2. What is recorded: nothing is logged anywhere. The status line is the record of a run, the generated file is the
   record of its result, and git is the history of both. This is deliberate: a view that wrote a log would be a
   view with state to keep consistent.
3. How you would know it is broken: `.github/workflows/validate.yml` runs `dod-wbs.mjs --selftest` and
   `dod-index.mjs --selftest` on every push to `main` and every pull request, alongside the two validators it
   already ran — the four commands of D29, which is the item that owns this (A16). The five checkers under
   `scripts/checks/` are run at close instead, by hand, because one of them needs a browser. There is no alert
   and no dashboard, because there is no service. The earlier wording here said `npm run validate` ran the
   selftest; it never did, and D29 is the item that now carries the claim.
4. This child introduces **twelve** checks: four rules inside `--check` and eight checkers that judge the
   build itself — `page-check.mjs`, `store-diff.mjs`, `rollback-check.mjs`, `paths-walked.mjs` and
   `tree-identical.mjs` under `scripts/checks/`, the two runners `scripts/selftest-all.mjs` and
   `scripts/ci-runs-selftests.mjs`, and `dod-wbs.mjs --selftest`. That set is derived by one rule — a
   script is a checker when it exports an `ASSERTIONS` registry — rather than counted here, because
   this paragraph said ten and then nine in the same breath while the tree held twelve (A27). Each of the
   twelve has all three inputs fixtured, because a verification script that passes
   vacuously is the failure this plan exists to prevent: for the eight checkers, D33 requires each to carry its
   own `--selftest` that plants one violation of every assertion it makes (reporting), runs a clean input
   (silent), and runs an empty input, which prints `checked 0 <things>` and never a bare success. The four
   `--check` rules are fixtured as follows. **D14** (grammar): reports on a
   malformed package line, silent on a valid tree, and on a plan with no section parses to `packages: []` with the
   status line naming what it checked. **D15** (ownership): reports on an orphan item, a double-owned item and an
   orphan step, silent on a valid tree, and on a section with no package lines reports every item as unowned
   rather than passing. **D16** (required at rubric 2): reports on a rubric-2 L or Epic with no section, warns on
   the rubric-1 equivalent, silent on a rubric-2 M, and judges an empty plan by its size and rubric like any
   other. **D17** (growth): reports on an adding amendment that names no package, silent on one that does, and
   prints `grew: none` — never nothing — when a plan has the section but no adding amendment. No empty input
   reads as a pass anywhere, in any of the twelve, because every one of them ends with a line saying what it
   checked and how many.

## Performance
1. Budget: `--wbs` under 5 s for 1,000 plans and under 2 s for 100, `--brief` unchanged, each as the median of five
   runs after a warm-up (D13). The hot path is file reading and parsing — one pass per file, asserted by a counter,
   which is the guarantee that matters more than the wall-clock number on any one machine.
2. Limits: eight version columns by default and a warning past 24 (D2); a name truncated at the width the compact
   view allows (D5); 1,000 rows proven in an export (D7). The eight-column cap came from a 100-column terminal —
   the valid case it excludes is a store with a long release history, which is why `--versions all` exists and
   prints everything.

## Rollout
1. Ships inside dod 0.2.0 with the other children; there is no flag, because every surface is opt-in by being a
   command nobody has to run. The user turns it off by not running it; the maintainer turns it off by releasing a
   version without the script.
2. Backward compatibility: plans with no `## Work breakdown` section keep checking green at rubric 1 and are
   warned, not failed (D16); the section and the ` · package:` field are ordinary text to every older checker
   (D30); `--brief`, `--check` and the index are unchanged, and no existing output gains or loses a line.
3. Rollback. **D30 is the authoritative sequence and this is a restatement of it** — the two said different
   things for one round, which is how the contradiction got in, so the rule now is that a change to the
   rollback is made in D30 and copied here, never the reverse (A12).
   (a) `rollback-check.mjs` prints the exact commit set and says which of D30's two cases the interval is
   in; run the one it names. If this child owns every commit after the base:
   `git revert --no-commit --no-edit <base>..HEAD`. If it does not — which is the case in THIS interval,
   where three commits touch only `shared` paths — a range revert would destroy that other work, so the
   rollback is path-scoped instead: restore every `exclusive` path to its state at the base, leave every
   commit that is not ours standing, and take each `shared` path the checker names to a hand merge. Either
   way the result removes `dod-wbs.mjs`, everything the child added under `scripts/checks/` and `scripts/`,
   `references/wbs.md` and the work-breakdown parser and checks from `dod-index.mjs`. This clause said only
   the range revert until A28: A24 changed D30 to two cases and did not copy it here, which is the drift the
   preamble above forbids, by the rule written after it happened once already (A12).
   (b) delete the four generated files (`wbs.csv`, `wbs.md`, `<slug>.html`, `<slug>.review.html`) from the
   store, and `scripts/checks/node_modules/` with them — `git revert` cannot remove it, because it was never
   tracked (`ignored`, item 4), so it is the one thing the rollback has to delete by hand.
   (c) stop. Retained, deliberately and by name: Playwright's browser cache under the OS temp root — outside
   the repository, shared with nothing, downloaded once per machine. Nothing else is retained, because nothing
   else is still there: every per-run temp root, every scratch clone and every SELFTEST's screenshots are
   deleted by the command that made them before it returns, which `paths-walked.mjs` asserts per command (A13). A real
   `page-check.mjs` run is the one exception and it is deliberate: its four screenshots are the evidence of
   that run, they go to the directory it creates and prints, and the inventory marks that directory `outlives`
   (A19). Nothing in the repository is involved either way.
   The rollback is still possible after data has been written, because the only data written *into the
   repository* is those four files and nothing reads them — no schema, no store field and no other plan depends
   on them. A plan written under the new rule survives the revert: the `## Work breakdown` section and the
   ` · package: W1.2` field are ordinary text to the older grammar. D30 runs all of (a), (b) and (c) in a
   scratch clone, asserts the reverted worktree is the tree at the base ref, and then checks the store with
   both the reverted checker and the pinned `skills/dod/tests/fixtures/dod-index.v0.1.mjs`.
4. Paths walked, by build step, each typed by what git must say about it — `repo` (tracked at HEAD after the
   build), `generated` (written into a store at run time: untracked, and gitignored when that store is inside
   this repository), `ignored` (inside the worktree, never tracked, with a `.gitignore` line as its proof) or
   `session` (resolving outside the worktree entirely). D32 checks each against `git ls-files` and `.gitignore`,
   not against a path prefix, and the same four definitions are stated there and nowhere else:
   step 1 `skills/dod/scripts/dod-wbs.mjs` `repo` (new); steps 2–4 the same file; step 5
   `skills/dod/scripts/dod-index.mjs` and `skills/dod/references/plan-template.md`, both `repo`; steps 6–7
   `dod-wbs.mjs`; step 8 `dod-wbs.mjs` and `dod-index.mjs` (their `--selftest` sections) — no file under
   `skills/dod/tests/` changes, and D30 and D32 read the pinned `skills/dod/tests/fixtures/dod-index.v0.1.mjs`,
   already in the tree at b152504, without writing it; step 9 `scripts/checks/page-check.mjs`,
   `scripts/checks/package.json` and `scripts/checks/package-lock.json`, all `repo` and all new —
   `scripts/checks/` **is** an installed package, the only one in this repository, nested exactly so the root
   stays dependency-free and `npm run validate` keeps working from a bare checkout — plus
   `scripts/checks/node_modules/` `ignored` (a `.gitignore` line is its proof: it lives in the worktree and is
   never tracked) and Playwright's browser cache at `<the OS temp directory>/dod-wbs-browsers`, `session` — one fixed directory
   under the OS temp root, reused by the install command and by every `page-check.mjs` run alike, which is what

   at run time `docs/dod/wbs-view.html` and `docs/dod/wbs-view.review.html` `generated` — both gitignored under

   `references/lifecycle.md` and `skills/dod/SKILL.md`, all `repo`; step 11 `scripts/checks/store-diff.mjs`,
   `scripts/checks/rollback-check.mjs`, `scripts/checks/paths-walked.mjs` and `scripts/checks/tree-identical.mjs`

## Out of scope
1. Excluded outright, so no builder fills the gap by guessing: editing a plan from a page (both pages are
   read-only renderings; a reviewer writes findings in the reviews file as they do today — a page that could
   edit a plan would need every rule the referee enforces, which is `dod-index.mjs`'s job, not a view's);
   colour in the terminal tree (D25 requires every meaning to be a word anyway); a single whole-store HTML page
   (the review page must be score-redacted and the plan page must not); and any scheduled or hook-driven
   generation (every surface here is a command someone runs).
2. Deferred, each to a named child of this epic: the `audit` command and its output surface → **`audit`**; the
   `enhance` command and its surface → **`enhance`**; the hook that would run a view without being asked →
   **`autonomy-hooks`**; the version bumps, the push and the public `dod-feedback` label → **`release-0-2`**.
   All four rows already exist in `docs/dod/dod-v0-2.md`'s `## Children`. By the owner's decision of 2026-09-19,
   epic items D24, D28 and D33 are satisfied here only for the surfaces this child ships, and their audit,
   enhance and hook halves stay open against those slugs.

## Also considered
- Rendering the tree from `README.md` instead of the plan files — rejected: the index is a generated snapshot, and
  a view that trusted it would show stale numbers exactly when the store is being worked on, which is when it is
  read.
- A single HTML page for the whole store rather than one per plan — rejected for now: the review page has to be
  score-redacted and the plan page must not be, and mixing them in one document makes redaction a rendering flag
  rather than a separate artifact.
- Colour in the terminal tree — rejected: D25's checklist would then need a no-colour mode to test, and every
  meaning would still have to be a word, so the colour would carry nothing.

The rubric's applicability list, one line each rather than silence:
- Compliance and legal — nothing applies: no personal data, no regulated content, no third-party terms beyond
  Playwright's Apache-2.0 licence, which is dev-only and not redistributed.
- Localisation — not applicable: every string is English and comes from the plan file, which is English; there
  is no message catalogue to translate and no date or number formatted for a locale.
- Running cost and quotas — zero: no service, no API, no storage. The only recurring cost is the one-off
  Chromium download of about 150 MB per build machine, on the builder's own disk, at `<the OS temp directory>/dod-wbs-browsers`
  (typed `session`, item 4) — once per machine, because that directory is fixed and reused, not made per run.
- Operational ownership — the repository's owner, as with every other script here. Nothing runs unattended, so
  there is nothing to be on call for.
- Documentation and changelog — `references/wbs.md` is the document (D24); the changelog line and the version
  bump belong to `release-0-2`, not here.
- Analytics — none, deliberately: `feedback-loop` is the only thing in this skill that reports anything
  anywhere, it is opt-in, and this child adds no event, counter or ping to it.
- Decommissioning — the rollback in item 3 is the decommissioning: revert, delete four files, stop. No data
  outlives it, because nothing reads the generated files.
- Support tooling — the review page is the support tool: when someone disputes a plan's coverage, `--html
  <slug> --review` is what they and the author look at together.
